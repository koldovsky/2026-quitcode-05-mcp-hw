# Підключення MCP-серверів LeadDesk (Task B)

- **Акаунти** (особисті чи одноразові, без клієнтських організацій і команд): Supabase — особистий акаунт, одноразовий порожній проєкт (його `project_ref` є в `.mcp.json`) · Vercel — особистий акаунт, у ньому єдиний проєкт: форк цього навчального репозиторію · Figma — не використовували
- **Третій сервер:** Playwright — чому саме він: не потрібен акаунт і немає місячної квоти викликів (Figma на Starter — 20 на місяць на все), а перевірка форми йде проти локального `npm run dev`. Його звуження теж можливе лише deny на боці Claude Code, але прапорці `--isolated` і `--no-webmcp` додають ще два шари.
- **Vercel CLI на цій машині:** не встановлено (`Get-Command vercel` нічого не знаходить), тож `vercel whoami` не виконується. Інструмента `use_vercel_cli` у списку інструментів сесії з Vercel теж немає. Шлях «MCP → `Bash` → локальний `vercel` під моїм CLI-токеном» закритий відсутністю CLI.

## Supabase: схема й сид

- Міграція `supabase/migrations/0001_leaddesk.sql` створює таблицю: `public.leads` (поля: `id`, `full_name`, `company`, `email`, `source`, `status`, `budget`, `message`, `created_at`; `status` обмежено п'ятьма значеннями через `check`; агент додав ще `budget >= 0` і увімкнув RLS без політик)
- Сид `supabase/seed/leads.sql`: 20 рядків, `lead_0001`–`lead_0020`, ті самі, що в `materials/leads.json` (порівняно програмно по всіх дев'яти полях, розбіжностей 0)
- Скільки інструментів Supabase видно в `/mcp` із моїм URL: 9
- Якими викликами створено схему й дані і що я схвалював вручну: `list_tables` (дозволений правилом `allow`), `apply_migration` (назва `leaddesk`), `execute_sql` (`insert` на 20 рядків) і `execute_sql` (перевірка: 20 рядків, 3 без бюджету, 5 статусів); кожен `apply_migration` і `execute_sql` схвалено вручну, відхилених не було

## Сесії: що вмикаємо разом

У кожній сесії — щонайбільше один сервер із правом запису; браузерний сервер — ніколи разом із Supabase. Для кожного кроку відкривав нову сесію в терміналі й вимикав усе зайве в `/mcp`, зокрема конектори claude.ai. Окрім серверів із `/mcp`, у терміналі автоматично підключається інтеграція `ide` (інструменти `getDiagnostics`, `executeCode`); вона в `/mcp` не показується. За записами сесій, `ide` (2 інструменти) була доступна в сесіях Vercel і трьох сесіях Playwright, а в сесії Supabase її не було. Це залишковий ризик: `executeCode` — інструмент, що може виконувати код, і формально це другий сервер із правом запису в тих сесіях, де він є, тобто межу «один сервер із правом запису» там порушено. Але **підтвердженого використання `ide` немає**: у записах усіх сесій Task B–E (Supabase, Vercel, три сесії Playwright, обидва прогони A/B, E2) викликів `mcp__ide__*` 0, а змін даних через неї не було: у сесії Vercel агент лише читав (`list_*`, лог білду), у сесії Playwright відправив форму в локальний застосунок записаними викликами `browser_*`. Правило `deny` для нього не додавав: ключа `ide` немає в `.mcp.json`, а префікси правил мають збігатися з ключами. Закривається запуском сесії в зовнішньому терміналі без підключення до VS Code: так зроблено в Task C (обидва прогони, `entrypoint: cli`, у списку інструментів лише один сервер; `docs/mcp/ab-generic-vs-domain.md:6`) і в бонусі E2. Сесії Vercel і Playwright із Task B запускали з VS Code, тому в них `ide` була. **27.11.2026 усі чотири сесії повторено без `ide`** (розділ нижче): у кожній рівно один сервер і 0 інструментів `mcp__ide__*`.

список інструментів на початку кожного транскрипту), а не знімком панелі.

`$env:ENABLE_CLAUDEAI_MCP_SERVERS = "false"; claude --strict-mcp-config --mcp-config "$env:TEMP\mcp-vercel.json"`
(файл з одним ключем із `.mcp.json`); на старті `/mcp` — один сервер, `/context` — без `mcp__ide__*`.
